pkg/runtime

design proposal draft 2026-08-03 · pi-go

A resident-instance manager for durable agents: it instantiates an agent when a request names a session, keeps it warm across turns, serializes runs against it, routes the run's event stream back to the caller, and evicts it when it goes idle or the pool is full. The store makes eviction safe; the runtime makes it automatic.

1. The problem

durable.New already documents the gap this package fills:

New does not track instances — each call returns a fresh one, and the caller owns instance discipline.

For the CLI, instance discipline is trivial: one session, one process, one instance. For a server it is the whole job. Every server built on pi-go today must hand-roll the same four things:

  • Instantiation. A request names a session ID; someone has to hold the map from ID to live instance, create on miss, and win the race when two requests miss at once. Rebuilding per request works — durable.New hydrates from the store — but pays hydration, artifact resolution, and seeding on every turn, and discards the in-memory state (the leaf position, ephemeral entries) that makes an instance more than its transcript.
  • Eviction. A long-running server cannot hold every session it has ever seen. Instances must be closed and dropped when idle, without closing one mid-run.
  • Request routing. Runs are strictly sequential per agent — a second Run while one is active fails its stream. Someone has to serialize.
  • Response routing. The run's events have to get back to the caller that sent the input, and only that caller — session-lifecycle events already have their own path (the Publisher).

None of this is application logic. All of it is the same in every server.

2. Where it sits

  agent      the loop
   │
  durable    + persistence, one session per instance
   │
  harness    + artifact compilation, mints durable agents
   │
  runtime    + instance discipline: many sessions, one process   ← this proposal
   │
  your server (HTTP/WS/queue — not the SDK's business)

The runtime imports durable and session only. It does not import harness — it takes a factory function, and a closure over harness.Agent is the expected but not required way to make one. Same relationship harness has to durable: composition without the lower layer knowing.

3. Key decisions

A factory in, instances out. runtime.New takes func(ctx, sessionID) (*durable.Agent[T], error). The runtime never constructs an agent itself and has no opinion about harness, catalog, store, or options — the factory closes over all of that.

Alternative rejected: accepting a *harness.Harness[T] directly. Convenient for the common case, but it would couple the runtime to the top of the stack and exclude agents minted by bare durable.New. Bought: the runtime works for any durable agent, and per-session configuration (working directory, overlays, model) is just code in the factory.

Checkout is the primitive; Run is the 90% verb. Acquire(ctx, id) returns the actual *durable.Agent[T] plus a release func. While any acquire is outstanding, the instance cannot be evicted (a refcount, not a lock — concurrent acquires of one session share the instance). Every durable verb — Branch, Fork, Compact, SetState, Transcript — is reached through the checkout, unmirrored.

Alternative rejected: mirroring the durable verbs on the runtime (rt.Branch(id, …), rt.Compact(id, …)). That API must chase every verb durable adds, forever, and adds nothing but the lookup. Cost accepted: a caller can hold a checkout too long and pin an instance; release discipline is theirs. Bought: a runtime API of five methods that never grows when durable does.

Run serializes per session: FIFO, waiting is ctx-bounded. rt.Run(ctx, id, entries…) acquires, waits its turn behind any active run on that session, runs, and releases when the stream ends. Two quick messages from one user become two turns in order, not one turn and one error. Cancelling ctx while queued abandons the wait; the input is never persisted.

Alternative rejected: surfacing durable's run already active to the caller and making every server write its own retry loop. Cost accepted: a queued message is a next turn — it cannot steer the run in flight, and nothing bounds the queue but callers' contexts. Both are real questions (see unknowns #3). Bought: the obvious server handler is three lines and correct.

Run returns a *durable.Stream, never (stream, error). A factory failure, a closed runtime, or a cancelled wait comes back as durable.Fail(err) — one error path, on the stream, exactly the invariant agent.Run and durable.Run already keep: errors, including pre-flight ones, surface on the stream.

Bought: response routing is nothing but handing the stream to whoever asked. The runtime adds no second event vocabulary and no subscription machinery — the run stream goes to the caller of Run, and session-lifecycle events keep flowing to whatever Publisher the factory installed. Fan-out to additional watchers is deliberately unsolved here (unknown #4).

Eviction is idle-only, and two policies compose. WithIdleTTL(d) sweeps instances whose last activity is older than d; WithMaxInstances(n) evicts least-recently-used idle instances when a miss would exceed n. An instance that is running, queued behind, or checked out is never evicted — capacity pressure with zero idle instances makes the miss wait, not the victim die.

Alternative rejected: pluggable eviction policies (WithEvictionPolicy(…)). Speculative flexibility with no consumer; TTL + LRU cap covers the known cases, and a policy interface can be extracted the day a third policy exists. Cost accepted: eviction discards in-memory state — see §7, which is honest about exactly what. Bought: bounded memory with two knobs a reader already understands.

Close drains. After rt.Close(ctx) begins, new work fails fast (ErrClosed on the stream); active runs get until ctx to finish; then every instance is closed. Store persistence is per message, so even a run cut off by the deadline is durable up to its last completed message — that guarantee is durable's, and the runtime inherits rather than restates it.

4. API

The whole surface. Five methods on the type, two options, one factory type, two sentinel errors.

// Package runtime manages resident instances of durable agents:
// instantiation on demand, per-session run serialization, idle
// eviction, and drain on shutdown.
package runtime // import "github.com/sonnes/pi-go/pkg/runtime"

// Factory mints the instance for a session ID. Typically a closure
// over [harness.Harness.Agent] or [durable.New]. Called at most once
// per resident lifetime of a session — concurrent requests for the
// same absent session share one call.
type Factory[T any] func(ctx context.Context, sessionID string) (*durable.Agent[T], error)

// New returns a Runtime. The zero configuration holds instances
// forever and without bound — pass WithIdleTTL and WithMaxInstances
// in any real server.
func New[T any](f Factory[T], opts ...Option) *Runtime[T]

type Option func(*config)

// WithIdleTTL evicts an instance whose last activity — run end,
// release, or durable verb — is older than d. Zero means never.
func WithIdleTTL(d time.Duration) Option

// WithMaxInstances bounds resident instances. On a miss at the
// bound, the least-recently-used idle instance is evicted; if none is
// idle, the miss waits. Zero means unbounded.
func WithMaxInstances(n int) Option

// Run routes entries to the session's instance — instantiating it
// if absent — and returns the run's stream. Runs on one session are
// FIFO; Run waits for its turn until ctx is done. All errors,
// including factory failures, surface on the stream.
func (r *Runtime[T]) Run(ctx context.Context, sessionID string, entries ...session.Entry) *durable.Stream

// Acquire checks out the session's instance for direct use of the
// durable verbs. The instance is not evicted while checked out; the
// caller must call release exactly once. Concurrent acquires share
// the instance — durable's own locking makes its verbs safe.
func (r *Runtime[T]) Acquire(ctx context.Context, sessionID string) (a *durable.Agent[T], release func(), err error)

// Evict closes and drops the session's instance now. It refuses —
// ErrBusy — if the instance is running or checked out. An absent
// session is a no-op. The next request rehydrates from the store.
func (r *Runtime[T]) Evict(sessionID string) error

// Resident reports the sessions currently instantiated, for
// observability. Order is unspecified.
func (r *Runtime[T]) Resident() []string

// Close drains: new work fails with ErrClosed, active runs get
// until ctx to finish, then every instance is closed. Idempotent.
func (r *Runtime[T]) Close(ctx context.Context) error

var ErrClosed = errors.New("runtime: closed")
var ErrBusy   = errors.New("runtime: instance busy")

Notes on shape:

  • Options are plain runtime.Option, not agent.Option. The extension-slot currency exists so options can ride one flat list down through layers; the runtime is above the option-consuming stack and its knobs configure the pool, not any agent. Mixing them into the agent list would imply they overlay per build, which they never do.
  • Acquire returning the naked *durable.Agent[T] means nothing stops a caller stashing the pointer past release. Documented as undefined behavior rather than prevented with a wrapper type — the wrapper would have to mirror every verb, which is the rejected alternative again.
  • There is no rt.Get-without-instantiating and no rt.Has. Reading a transcript without wanting an instance is a session.Store read; the runtime is only for callers that want the live thing.

5. Instance lifecycle

                 miss on Run/Acquire
                 (singleflight: one factory call
                  per absent session)
   ┌─────────┐  ───────────────────────▶  ┌─────────┐
   │ absent  │                            │  idle   │◀────────────┐
   └─────────┘  ◀───────────────────────  └─────────┘             │
        ▲        evict: IdleTTL sweep /     │    ▲                │
        │        LRU at MaxInstances /      │    │                │
        │        explicit Evict             ▼    │                │
        │        (agent.Close + drop)     ┌──────────┐   run ends │
        └──── never from here ─────────── │ running/ │────────────┘
              (running, queued-behind,    │ acquired │
               or checked-out instances   └──────────┘
               are unevictable)

Last-activity is bumped on run end, release, and any acquire — an instance's TTL clock measures quiet time, not lifetime. Rehydration after eviction is durable.New's resume path: history from the store, leaf at the last appended entry, crash-repair included. That path already exists and is already tested; the runtime adds no second resume mechanism.

6. DX walkthrough

Wiring — once, at startup

store, err := sessionfs.New[chat.State](dir)          // or your Postgres store
h, err := harness.New[chat.State](
    harness.WithCatalog(cat),
    harness.WithDefaultModel("anthropic/claude-fable-5"),
    harness.WithSkills(fsres.Skills(".claude/skills")),
    durable.WithStore(store),
)

rt := runtime.New(
    func(ctx context.Context, id string) (*durable.Agent[chat.State], error) {
        return h.Agent(ctx, durable.WithSessionID(id))
    },
    runtime.WithIdleTTL(15*time.Minute),
    runtime.WithMaxInstances(512),
)

The factory is where per-session policy lives, as plain code — look the session up in your own database and overlay its working directory, its model, its resolvers:

func (s *server) mint(ctx context.Context, id string) (*durable.Agent[chat.State], error) {
    ws, err := s.db.Workspace(ctx, id)
    if err != nil {
        return nil, err
    }
    return s.h.Agent(ctx,
        durable.WithSessionID(id),
        harness.WithWorkDir(ws.Root),
    )
}

The chat handler — the 90% path

func (s *server) handleMessage(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("session")

    stream := s.rt.Run(r.Context(), id, durable.Text(r.FormValue("text")))

    w.Header().Set("Content-Type", "text/event-stream")
    for evt, err := range stream.Events() {
        if err != nil {
            writeSSEError(w, err)
            return
        }
        writeSSE(w, evt)              // events are durability receipts:
    }                                 // anything the client renders is already stored
}

No lookup, no create-on-miss, no lock, no "is it already running", no cleanup. The three failure shapes — factory error, closed runtime, cancelled wait — all arrive as the stream's error, so the handler has one error path.

Durable verbs — the checkout path

func (s *server) handleRewind(w http.ResponseWriter, r *http.Request) {
    a, release, err := s.rt.Acquire(r.Context(), r.PathValue("session"))
    if err != nil {
        http.Error(w, err.Error(), http.StatusServiceUnavailable)
        return
    }
    defer release()

    if err := a.Branch(r.Context(), r.FormValue("entry")); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }
    w.WriteHeader(http.StatusNoContent)
}

Shutdown

ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
if err := rt.Close(ctx); err != nil {
    log.Printf("runtime: drain incomplete: %v", err)   // runs cut off are still
}                                                      // durable per message

7. What eviction costs

Eviction is safe because durable persistence is per message. It is not free. Honestly:

Survives evictionLost on eviction
The transcript, per message — input persists before the run, every produced message at its message_end The leaf position. A rewind via Branch is in-memory by design; rehydration resumes at the last appended entry. An evicted session silently un-rewinds. (Unknown #2.)
Session state — a fold over persisted StateEntrys Ephemeral entries — never stored, by definition
Crash repair — dangling tool calls patched on resume The build snapshot — the next instance re-resolves artifacts, which is usually a feature (edits arrive) and occasionally a surprise (the prompt changed mid-conversation)
Seeding correctness — the leaf-pointer guard means a resumed session never re-seeds Warm subprocess state, for CLI-backed agents — Close kills the child process (unknown #7)

8. Unknowns

Ordered by how much they could bend the design. The first two are the ones to settle before writing code.

1 · Detached runs and reconnection

In this proposal the caller's ctx owns the run: client disconnects, run cancels mid-tool. For a chat product that is often wrong — the user closes their laptop, the agent should finish, and the client should re-attach and catch up. Detached runs pull in a chain of machinery: a runtime-owned run context, a per-session event buffer, replay from an event or leaf cursor, and an Attach(id) verb — most of a broker, which the durable layer explicitly refused to be.

ship attached-only first; it is what the synchronous Run semantics honestly support. Detached execution is a design of its own — likely a separate layer or package — and bolting a buffer onto v1 would prejudge it.

2 · Eviction silently un-rewinds a branched session

The leaf lives in memory on purpose ("a rewind is a property of a working instance, not a stored fact"). A runtime that evicts turns that deliberate choice into a booby trap: rewind, go idle 15 minutes, come back, and your next turn grows from the old leaf. Options: (a) persist the leaf, reversing a documented session-layer decision; (b) pin instances whose leaf ≠ last appended entry, letting one rewound session defeat the memory bound; (c) let the application record the leaf in session state and re-Branch in the factory; (d) document it and accept the surprise.

(c) — it needs zero new mechanism and keeps the layering honest. But it is a sharp edge every server team must know about, which argues it at least deserves a loud place in the runtime's package doc, and possibly a runtime-level helper later.

3 · Busy semantics: queue, reject, or steer

FIFO-wait makes the second message a next turn. Products increasingly want a third thing: a message that lands inside the active run (steering, à la "actually, stop and try X"). That is an agent-loop capability pi-go does not have, and no runtime queue can fake it. Also open: should the wait be bounded by anything besides the caller's ctx (a depth cap per session?), and should there be a TryRun that returns ErrBusy for callers that would rather show "agent is working" than block?

FIFO-wait only, no depth knob until a real server needs one. Steering is upstream loop work, out of the runtime's hands.

4 · Fan-out: the second watcher of a session

The run stream goes to whoever called Run. A second browser tab watching the same session gets nothing. Durable's answer is the Publisher — but session events don't carry the streaming deltas, one publisher exists per agent, and the factory owns it. If the runtime installs its own fan-out publisher it collides with the factory's; if it doesn't, every app builds fan-out alone (which the no-broker decision says is fine). Slow subscribers, replay, and backpressure are all lurking behind this door.

stay out in v1 — same reasoning as the durable layer's "every application that needs fan-out already has a way to do it." Revisit together with unknown #1; they are the same broker in two costumes.

5 · One process is load-bearing

The design assumes all requests for a session reach one process. Two replicas each instantiating a session won't corrupt it — durable's concurrent instances grow sibling branches — but users would see a conversation that forks invisibly per request. Sticky routing, a distributed lock, or lease-in-store are all plausible; all are infrastructure the SDK has so far refused to carry.

declare single-process scope loudly and leave routing to the deployment. Perhaps the one cheap assist: a store-level lease hook, someday, as an optional interface.

6 · Capacity pressure with zero idle victims

At MaxInstances with every instance running, a miss waits. Under sustained overload that is an unbounded convoy of waiting requests — the classic thundering-herd shape. Options: fail fast with a capacity error, wait with no bound but the ctx (proposed), or a semaphore with a queue cap.

ctx-bounded waiting matches the rest of the design; servers already run request timeouts. But this is the knob most likely to grow once a real deployment hits it.

7 · Eviction cost is wildly asymmetric across agent kinds

Evicting an in-process instance costs a hydration on return. Evicting a CLI-backed agent (agent/claude, codex, cursor) kills a subprocess whose restart costs seconds and whose own internal session state may not round-trip through pi-go's store at all. One TTL for both is crude. Per-factory TTL? A Cost hint on the instance? Or is a CLI-backed server simply expected to set a long TTL?

one TTL, documented. Evidence before knobs.

8 · Fork escapes the registry

Acquire hands out the real agent; calling Fork on it mints a child instance the runtime has never heard of — unevicted, untracked, and a second live instance if someone later asks the runtime for the child's ID. Options: document ("fork through the store: release, then Run against the new ID"), or an Adopt verb, or intercepting Fork — which needs a wrapper type, the thing this design keeps refusing.

document the pattern; adoption only if it proves common.

9 · The name

pkg/runtime collides with the stdlib's runtime — any file importing both must alias one, and grep-ability suffers. Candidates: keep runtime (few app files import stdlib runtime), host, pool, resident.

keep runtime; the collision is rare in application code and the word is exactly right. Decide before the first release, not after.

9. Non-goals

  • Not a server. No HTTP, no websockets, no wire protocol. The runtime ends at "here is a stream"; transport is the application's.
  • Not a broker. No subscriptions, no replay, no delivery guarantees — inherited verbatim from the durable layer's no-broker decision, and revisited only together with detached runs.
  • Not a scheduler. No priorities, no cross-session fairness, no rate limiting. FIFO per session, first-come across sessions.
  • Not distributed. One process. See unknown #5.
